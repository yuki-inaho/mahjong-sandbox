## 1. 作業目的

### 1.1 ゴール要求分析

利用者の目的は、自作麻雀の対局ログを一般的なmjaiの `.mjson` 形式へ置き換え、外部の実牌譜もAIエージェントが解析できるようにし、実例に基づく失敗先行のテストで品質を確認することです。追加依頼に従い、現状を厳しくレビューし、write/reviewスキルを用いた作業書、専用ブランチ、検証後のマージまで実施します。

明示要求は、現状調査と辛口レビュー、mjsonへの移行、パーサとAI研究用の観測、実牌譜による事例テスト、TDD、作業書、ブランチからマージまでです。従前のRustコア、宣言ルール、契約、Kani/Lean、ADR、JS/TS/WASM、TOML設定、既存証跡の保存も維持します。

成功は、外部の実牌譜を入力として解析・観測を取得でき、自作対局の既定出力も同じイベント形式となり、型・CLI・SDK・WASMの公開経路から利用できることで判定します。パーサだけの追加や、拡張子だけの変更では達成としません。互換性の検査は固定した入力と仕様に対して行い、全mjai派生実装への適合や全麻雀規則の合法性証明を主張しません。

暗黙制約は、古い対局再現機能と情報公開境界の維持、途中切断の明示、入力上限、未知値の黙った補正禁止、個人情報・転載制限データを公開物へ含めないことです。既存の独自完全再生は明示的な互換形式として保持します。外部の赤牌・加槓・複数和了等を既存coreの限定規則へ無理に適用しません。新しいAI算法の強度向上、オンライン対戦、三麻エンジンの実装、学習済モデルの配布は今回の目的ではありません。

### 1.1.1 途中の追加方針：相互変換と拡張の余地

利用者から、形式間の変換や拡張用の包みを設ける方針も許容し、実装しやすい構成で進める旨の追補を受けました。標準のmjaiイベントを交換形式として保ち、既知項目の型と追加JSON値を `ParsedEvent.raw` で併せて扱います。AI用の観測出力は `schema_version`、元の行番号、イベント種別、視点別観測を持つ別の構造です。利用者ごとの説明・評価などは生の標準イベントの必須項目へ混ぜず、追加欄または観測を包む構造で拡張できます。

変換能力は情報の保持範囲で区別します。旧replayからmjsonへの変換は実装します。mjsonの追加JSON値は解析後にも保持しますが、元の空白・キー順まで一致するbyte列の保存ではありません。mjsonにない乱数種・内部の見送り操作を復元して旧replayへ戻す処理、視点別観測から他家の伏せ牌を復元する処理は提供しません。この区別と拡張時の変更箇所をログ仕様とADRへ記録し、現在の既定出力・解析・検証・マージの受入条件を維持します。

## 2. 作業内容

### フェーズ1：調査・設計（手順1〜4）

既存の `crates/suzume-api/src/logging/`、`src/game.rs`、CLI、SDK、WASMを調査します。参照先は `NikkeTryHard/tenhou-to-mjai` の固定版です。mjsonはJSON Linesのイベント表現で、圧縮有無は拡張子だけでは判定できません。独自操作履歴と外部イベントを同一視せず、実牌譜の赤牌・未知牌・多重和了・流局の表現を保持する型を設計します。

実牌譜の取得元、固定commitとSHA256、元牌譜と変換後データ、期待イベント・局数・得点を実装調整の前に確定します。データ本体は必要に応じ検証専用に取得し、公開リポジトリへ転載しません。合成の境界テストは実牌譜と明確に区別します。性能向上やAI強度の定量目標は利用者から指定されておらず、未測定の改善率を合格条件へ追加しません。

#### 入力集合と正解の固定（M-02/M-06）

参照リポジトリは `https://github.com/NikkeTryHard/tenhou-to-mjai`、固定commitは `f08b4e0f7d96b57d0099b9b2e5eb6dd5c4e5f4eb`、対象は `crates/convlog/tests/testdata/*.json` の20事例です。全件を選択し、成功する事例だけを選び直しません。研究担当の事前集計は変換後2,310イベント・23局であり、これは新パーサの成功件数ではありません。各事例の元データSHA256、変換後SHA256、イベント別件数、局数、最終持点を検証用manifestへ固定し、手順2でその保存先を本書へ追記します。

| 事例 | 実牌譜由来の確認 | 事前のイベント数・局数 | 最終持点の期待値（席0〜3、点） |
|---|---|---|---|
| `ranked_game` | 原牌譜のrefを非公開領域で確認済み | 316イベント・3局 | `[21100,55000,-4900,28800]` |
| `suukantsu_1` | 原牌譜のrefを非公開領域で確認済み | 243イベント・2局 | `[38000,29000,-24000,57000]` |

この2事例は原牌譜の識別子を確認した実牌譜由来の入力です。他の18事例は外部リポジトリの回帰用入力として扱い、すべての対局の実在性を確認したとは表現しません。実装で生成する合成の正常・異常例はこの20件の分母へ加えません。元牌譜の点数・局の情報から期待値を求める処理を、新パーサの出力から期待値を作る処理と分離します。固定版変換器との一致は形式互換の根拠であり、牌譜中のすべての和了・役・得点を独立に再計算した証明ではありません。

取得先は `dist/mjai-real/upstream/`、変換後の生データは `dist/mjai-real/` に限定します。`dist/verification/` には集計・hash・コマンド・診断位置のみを保存し、牌譜本文、対局者名、丸ごとのJSONを記録しません。既存 `.github/workflows/platform.yml` は `dist/verification/` を公開するため、この区分を守る必要があります。Git・配布書庫・CI artifactの対象に `dist/mjai-real/` が入らないことを手順12で検査します。

ネットワーク取得失敗またはhash不一致は当該事例を失敗とし、キャッシュは元・変換後hashが一致した場合だけ再利用します。20件のいずれかが未実行・失敗ならD2は未完了です。点数の保存は各入力の開始持点と供託から評価し、外部牌譜へ自作coreの初期総額100,000点を一律に当てはめません。未知牌・点数欠落は不明として保持し、既知値へ補完して合格させません。

### フェーズ2：実装（手順5〜10）

まず名前付き事例を記述し、実装前の失敗ログを保存します。パーサは型・入力上限・イベントの順序・牌の増減・点数/供託を検査し、視点別観測では他家の伏せ牌を返しません。ログの意味検査にも行番号とイベントを含めます。外部データに未記録の情報は不明として扱います。

書込み器は局面の差から意味イベントを生成し、内部の各応答を外部の副露へ誤変換しません。初期親ツモは配牌13枚から分離します。通常の出力をmjsonへ移行し、旧replay/publicは明示指定で維持します。中断は正常終了と区別します。TSは構造解析、Rustは局面の意味解析という責務を明示し、WASMも同じRust実装を使います。

圧縮の判定方法、展開を担当する入口と展開後の上限、APIの要求名・返却型、拡張フィールドの保存先は手順3で `docs/logging/mjai-compatibility.md` とADRに固定し、関連する実装担当へ同じ版を共有します。実牌譜の読込み・公開観測の復元から、未対応規則を含む既存coreの合法手マスクや完全再生を生成できるとは扱いません。既存の独自replay形式には、従来のseed・操作列による完全再生検査を残します。

担当範囲内の実装とテストは並行準備し、主担当が本書の順に検収します。パーサ担当はmjaiの型・reader・state・parserテスト、主担当はwriterと設定・CLI、別担当はSDK/公開API、調査担当は取得・実牌譜検証を所有します。共有ファイルの変更は主担当が調整します。

### フェーズ3：検証・公開（手順11〜13）

既存テストと形式検証、生成物同期、実WASM/SDK、配布消費を行い、変更箇所への独立レビューを実施します。新しい実牌譜の結果は既存の検証結果を上書きせず別記録へ残します。必要CIを確認し、PRの差分と対象commitを照合してからマージします。

## 4. 作業に使用するコマンド参考情報

Rust/Cargoが主実行系です。Python補助は標準ライブラリのみで `uv run --no-project python ...` を使用します。既存の `scripts/bootstrap.py` / `scripts/doctor.py` と `tools/versions.json` に固定版があります。`pyproject.toml`、`uv.lock`、`justfile` は存在せず、存在しない `uv sync` や `just` を要求しません。

```sh
python3 scripts/bootstrap.py --profile full
source dist/tools/activate.sh
python3 scripts/doctor.py --profile full
cargo test --workspace --locked
cargo test -p suzume-api --test mjai_parser
cargo test -p suzume-api --test mjai_writer
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo run --locked -p suzume-api --bin export-schema -- --check
uv run --no-project python scripts/generate_protocol_ts.py --check
uv run --no-project python scripts/verify_mjai_real.py
uv run --no-project python scripts/verify_platform.py --profile full
uv run --no-project python scripts/package.py
```

追加予定コマンドは実装後に実入口と照合します。利用環境の一時パスや認証情報は公開資料へ記録しません。導入失敗を既存道具で黙って代替せず、実際に使った版を記録します。

上の有効化はPOSIX shellの例です。Windowsではbootstrapが生成する `dist/tools/activate.ps1` をPowerShellで読み込みます。`uv` がない場合は明示的に導入して版を記録します。bootstrap/doctorの `python3` は導入を開始するための既存Pythonを使用します。API型を変更した際は、`export-schema` と `scripts/generate_protocol_ts.py` をそれぞれ `--check` なしで生成してから、上記の同期検査を実行します。
