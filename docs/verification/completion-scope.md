## 検査の実行条件

- 自動検査はverify-workdoc-completion付属の `run_recorded_check.py` で実際に起動します。任意の成功JSONを実行証明へ変換しません。
- 最終ソースの固定後に検査します。KaniとLeanは宣言・実装・生成物のSHAを固定し、検査後の同一性も確認します。
- 既存のKani成功記録は履歴として保持します。付属記録器の形式を満たす最終検査は1回実施します。内容が変わらない場合の追加反復は不要です。
- `simulation-32` は `cargo run --release -- --simulate 32 --seed 0` を実行します。失敗した試合を除外して成功率を出しません。
- 端末入力は主担当がPTYを起動して確認します。実行したコマンド、入力、観測した画面、終了状態を保存し、手動観測と自動検査を区別します。
- `ui-evidence` はその観測記録と実際の出力ファイルのSHAを照合する検査です。この照合だけで端末を操作したことにはしません。
- `source-hashes` は固定したソース一覧と検査後の実ファイルを照合します。SHA一致を意味上の正しさの代わりにはしません。
- 最終公開後に `git-final` を実行し、HEAD一致と未保存変更なしを確認します。結果を作業書へ埋め込んで相互依存するSHAを作らず、最終監査の記録は作業書の外側に保持します。

## 対象外を成功へ読み替えないための境界

形式検証はC-01〜C-06の基本契約に対するものです。役判定・局進行・端末全体の形式証明ではありません。初版で採用しない規則や他OSで未実行の検査は、[規則](../rules/riichi.md) と [検証範囲](README.md) の記載を維持します。これらの境界を口実に、ここに残した必須の実対局・実コマンドを省略しません。

未完了作業と阻害要因は状態記録に残します。完了監査が通るように空配列へ変更すること、DoDを削除すること、失敗・時間切れを成功にすることは禁止します。
