# ADR-0003：共通宣言、Rust契約、Kani、Leanを対応付ける

- 日付：2026-11-23
- 状態：採用、基礎契約を実装・検証済み。対局全体の形式証明は対象外。
- 関連：作業書TR-02〜04、[契約一覧](../contracts/README.md)、[検証範囲](../verification/README.md)

## 背景

利用者は、Rustによる麻雀の独自実装に加え、宣言的なルール、契約に基づく処理、Kaniによるコード検査、Leanによるルールとコードの一貫性の証明を求めています。独立した二つの仕様を書くだけでは、変更時に意味がずれる可能性があります。一方、対局・役判定・端末入出力まで含めたRust全体をLeanの意味論に変換する基盤は、このリポジトリの開始時点では存在しませんでした。

[Go-Lean](https://github.com/Mal-Pat/Go-Lean) は、ルールの中核を状態と操作から成功・失敗を返す関数として分離しています。その責務の分け方を参照します。本プロジェクトはRustを実行系として保ち、Leanを数学的なモデルと証明に使います。参照先のソースは転用しません。

## 決定

1. `rules/riichi.rules` に採用規則と数値を宣言し、`rules/contracts.json` にC-01〜C-06の合法条件・事後条件を式木で宣言します。
2. 依存ゼロのPython生成器で、RustとLeanの定数・比較仕様を生成します。未知キー、未対応値、未対応演算子、生成物の不一致を拒否します。
3. ゲームが呼び出すRust関数は独立に実装します。Kaniは任意の元の整数入力から生成された数式へ対応させ、成功値・拒否・状態保存を検査します。
4. Leanでは同じ生成式を用いたモデルについて、保存則、境界、リーチの制約などを証明します。数学的な整数とRustの有限整数の差は、Kaniで変換と算術境界を検査します。
5. 基本契約の外にある役判定・局進行・画面には、具体例のテストと実行時不変条件を適用します。形式証明の対象を広く見せません。

## 比較した案

| 案 | 利点 | 採用判断 |
|---|---|---|
| Rustテストのみ | 作業量が少なく、対局例を追加しやすい | 利用者のKani/Lean要求と任意入力の検査を満たさないため採用しない |
| RustとLeanの仕様を別々に手書き | 各言語に自然な表現を使える | 二つの仕様の同期を手作業に依存するため、共通宣言を加える |
| Rust全体の意味論をLeanへ移す | 対局全体の同値性へ進める余地がある | 対応基盤と証明量が大きい。現時点で成立済みとは扱わず、別の設計課題とする |
| 基礎契約の共通宣言＋Kani＋Lean | 実装をRustに保ち、有限入力のコード検査と数学的証明を結び付けられる | 採用。生成器とツールの信頼境界を明記する |

## 責務と失敗時の扱い

宣言の変更者は対応範囲と意図を定めます。生成器は宣言を検査して出力し、実装者はその条件を満たす関数を作ります。KaniとLeanの成功はそれぞれの対象に限ります。呼び出し側は、門前・聴牌などの事実が正しいことと、全体の状態が整合することを確認します。

点数移動は両側の算術検査後に書き込み、失敗なら元の状態を返します。生成物の不一致、検証の失敗、展開不足、時間切れは成功へ読み替えません。展開不足の検査を無効にして先へ進むこともありません。

## 結果と未解決点

18個のLean定理と6個のKaniハーネス、および5件の否定検査を実行して成功を確認しました。詳細は `docs/verification/logs/` の実行記録に残します。初回に点数ハーネスの内部配列比較で展開不足が生じたため、同じ意味を持つ5要素の比較に置き換えました。

生成器そのものの意味保存は未証明です。RustからLeanへの完全な意味論の変換も行っていません。仕様を拡張するときは、具体的な不具合や新しい規則を基に、どの条件を新たな契約・定理にする必要があるかを判断します。証明数を増やすためだけに、実際に呼ばれない関数や自明な定理を追加しません。

## 0.2.0での境界の補強

外部APIを設ける前のレビューで、生成器が式の型を推論していないことと、比較用仕様の関数が外部へ公開されていることを確認しました。例えば移動後枚数を任意のu16として扱うC-03の加算には、元のKaniハーネスが渡す値より広い入力域でオーバーフローの余地がありました。既存のKani成功を、生成仕様の全公開型の安全性へ拡大できないため修正します。

生成仕様はcrate内に限定し、構造・型・短絡条件に基づく整数範囲を生成前に検査します。C-03の移動後枚数とC-04Pの前後残高・金額へ、実Rust関数が保証する入力域を明示しました。両言語のリテラルにも型を付け、変数のない `0 - 1` がLeanだけ自然数として解釈される余地を取り除きます。負数の除算・剰余は対応させず、非負の被除数と正の除数に限定します。

より汎用的な数式コンパイラや生成器の形式証明へ一度に置き換える案に対し、今回は小さな式木と保守的な範囲検査を採用しました。受け付けられる式は限定されますが、拒否条件と信頼境界を明示でき、既存の6契約を維持できます。

19件の生成器回帰、実Rust/Leanでの7関係・19具体例、更新後のKani6ハーネスとLean18定理で検査しました。Leanの定理本文の変更は不要でした。これは生成器全体の意味保存証明ではありません。範囲検査で表せない演算や契約が必要になった場合は、入力域・算術意味・検証方法を再設計します。詳細と実証跡は [公開境界と生成仕様](../contracts/platform-boundaries.md) にあります。
