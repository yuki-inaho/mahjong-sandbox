# ADR 0002：ルールを宣言し、操作を原子的に適用する

日付：2026-11-23
状態：採用。実際の呼出しと検査結果は作業書・検証記録で確認します。

## 背景

ルールを宣言し、契約に基づいたゲームとして実装する要求があります。
麻雀はローカル規則の差が多く、何が実装されているか不明だと、判定テストや証明の前提も曖昧になります。
参照したMiHaJongは多数の設定を持ちますが、本実装はまず一つの明示した規則を対象にします。

## 決定

採用規則の正本を `rules/riichi.rules` に置きます。RustとLean用の定数を決定的に生成し、
検査時に宣言と生成物の不一致を拒否します。未対応の値は拒否し、別の値へ黙って置換しません。

対局の公開操作は、合法性の確認、候補状態への適用、不変条件の確認、状態の確定の順に処理します。
失敗した操作は元の状態を保ちます。牌・点数の移動には形式検証対象の小さな契約関数を使用します。
成功時も、牌の総数と所在、持点と供託の総和など、ゲーム全体の条件を実行時に確認します。

## 比較した案

- 各モジュールへ定数を手書きする案は、変更時に食い違いが発生するため採用しません。
- すべてのローカル規則を切り替え可能にする案は、組合せごとの検証範囲が増えるため初版では採用しません。
- 正常時だけassertする案は、不正入力で状態を壊す余地を残すため公開操作には使いません。
- 状態を複製してから確定する案を採用します。136枚の小規模な対局では、巻き戻し処理を分散させるより理解しやすいためです。

## 契約と責務

呼出し側は操作する席と選択を渡します。対局処理は合法手、必要な牌、支払条件を検査します。
UIは表示と入力解釈を担当し、UIでボタンを隠しただけで契約を満たしたとは扱いません。
判定処理は牌構成と和了条件を受け取り、成立する役と点数を返します。

## 検証と限界

宣言の同期、不正操作時の状態同一性、牌と点数の保存を検査します。
定数の生成は、宣言の自然言語の意味と役判定全体の同値を自動証明するものではありません。
LeanとRustの関係はADR 0003の対応範囲に限定します。

## 根拠

要求はTR-02、TR-05。規則差の参考は [MiHaJong](https://github.com/MihailJP/MiHaJong)。
純粋な操作適用の参考は [Go-Lean](https://github.com/Mal-Pat/Go-Lean) の `Game.step` と入力拒否です。
