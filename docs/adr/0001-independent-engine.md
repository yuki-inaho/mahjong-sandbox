# ADR 0001：標準ライブラリで独立した対局処理を作る

日付：2026-11-23
状態：採用。実装と検証の完了は作業書で別管理します。

## 背景

Rustによる独自実装、端末で遊べること、可搬性・保守性・再利用性が要求されています。
開始時点のリポジトリは空でした。参照先には端末、学習、GUI、Lean内の操作画面と
異なる構成があり、そのまま移植する共通の実装基盤はありません。

## 決定

`tile`、`hand`、`scoring`、`contracts`、`game`、`ai` をライブラリに分離し、
`main` と `ui` を端末用の境界にします。対局処理は `Action` を受け取り、
成功か理由付きのエラーを返します。CPUも合法手と公開情報を受け取って操作を選びます。
初版は標準ライブラリだけを使います。入出力は行入力とANSI表示を組み合わせ、
制御文字を使わない表示を明示した選択肢として用意します。

## 比較した案

| 案 | 利点 | 採否の理由 |
|---|---|---|
| 既存の麻雀ライブラリに依存 | 実装量を抑えられる | 独自実装という要求と合わない |
| TUIライブラリを先に導入 | キーイベントとレイアウトが豊富 | 初版の行入力には不要な依存。後で表示境界だけ置換可能 |
| 画面とルールを一体化 | 最初の画面を早く作れる | 検証と再利用のために分離が必要 |
| 標準ライブラリと独立した対局処理 | 依存が少なく、検査対象が明確 | 採用。高度な画面操作は初版で限定される |

## 検証と限界

`game` が端末やファイルを参照しないこと、CPUへ隠れた牌情報を渡さないこと、
通常のCargoでビルド可能なことを確認します。OSごとの実機検証は、実行した環境だけを記録します。
標準ライブラリのみという事実は、すべての端末で表示幅が一致する保証ではありません。

## 再検討条件

矢印キー、マウス、複雑な画面再描画が必要になったら、ルールを変更せずUI境界の依存を再検討します。

## 根拠

要求は本作業書TR-01・TR-05。責務分離の参考は [Go-Lean README](https://github.com/Mal-Pat/Go-Lean)
と [mahjong-ai README](https://github.com/clarkwkw/mahjong-ai)。実装の所在は `src/lib.rs` です。
