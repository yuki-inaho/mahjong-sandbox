# 注釈付き記録に向けた現状の辛口レビュー

対象は `d44f5ee499102fd35d81fbba5eb1e42da2e0a318` です。前回のマージ済み実装と検収は保持し、今回の相互変換・注釈保存という要求に対して不足を評価しました。2名の独立した読取り調査と合成入力による再現を使用しています。

## 評価

**解析器としての受入と、再保存して情報を保持できることは別です。現状の `raw` という名前だけを根拠に、損失のない変換を実装できると判断してはいけません。** 保存用の正本と受入テストが不足しています。

| 重要度 | 指摘・根拠 | 利用者への影響 | 今回の対応・受入 |
|---|---|---|---|
| 高 | `reader.rs` の `UniqueValue` とSDK `validation.ts` は拡張数値を数値型へ変換する | `9007199254740993e0` は丸められ、`1e-400` は0へ変わる。再保存後の分析情報を原値と誤認する | 原イベント原文を保持し、値へ再変換せず包装・取出しする |
| 高 | 型付き `Event` の再保存は追加項目と `deltas:null` を落とし、`uradora_markers` を正規名にする | 型は解析には有用だが、保存の正本に使うと情報が失われる | 型付き値と原文を分け、null・別名・未知項目の保持を検査する |
| 中 | 包装を `JSON.parse` → `JSON.stringify` してから既存パーサへ渡すと、`actor:1.0` が整数へ変わる | 不正な既知項目が包装によって受理される | 包装内の元の字句範囲を検査へ渡す |
| 中 | `state.rs` の `contains_red` は原JSONのすべての文字列を走査する | `start_game.extra.annotation="5mr"` を加えるだけで `red_events` が0から1へ変わる | 既知牌項目へ限定。以前の文書どおりの挙動であるため、契約変更として明示する |
| 中 | `verify_mjai_real.py` は固定SHA・イベント数・解析集計を検査するが再保存を検査しない | 変換機能を足しても全イベントの欠落・置換を検知できない | 全20件の原文・順序と4席観測を比較し、改変を拒否する対照を追加する |

## 再現した数値の例

| 入力字句 | Rustの解析値を保存した結果 | SDKの解析値を保存した結果 |
|---|---|---|
| `9007199254740993e0` | `9007199254740992.0` | `9007199254740992` |
| `1e-400` | `0.0` | `0` |
| `0.12345678901234567890123456789` | `0.12345678901234568` | `0.12345678901234568` |
| `18446744073709551617` | `1.8446744073709552e+19` | 安全整数外として入力を拒否 |

これは外部牌譜本体を公開せずに再現できる合成入力です。型付き値での数値の近似表現自体を禁止する修正ではありません。保存する原文と近似値の役割を明確にします。

## 維持できている点と限界

観測出力へ原イベントや他家の手牌が混入する問題は確認していません。既存の正常EOF検査、一時ファイルからの非上書き公開、固定20事例の入力集合は引き続き利用できます。今回も全mjai派生形式への適合、全麻雀規則の合法性、全得点の独立再計算までは保証しません。

修正の具体契約は [注釈付きmjai仕様](../logging/annotated-mjai.md)、判断は [ADR 0008](../adr/0008-annotated-mjai.md) に記載しています。実装前の失敗と修正後の成功は新しい作業書で別々に記録します。
