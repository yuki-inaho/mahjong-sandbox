# 注釈付きmjai：Rust・CLIの独立実装レビュー

## 対象と判定

対象は `feat/mjai-annotated-records` の作業中差分、主に `crates/suzume-api/src/mjai/{annotated,reader,state,types}.rs` と `crates/suzume-api/src/bin/suzume-api.rs` です。レビュー担当はこのRust mjaiモジュールとCLIを実装していません。自ら実装したSDK・API要求の変更は独立レビューの対象から除きました。

**初回判定：修正または契約の明確化が必要です。** 原文・字句・重複・注釈境界に新たな破損は確認していません。公開後の報告失敗について、CLIの終了状態と作業書の完了条件に不一致を1件再現しました。修正確認は本書へ追記し、初回の記録を消しません。

## 指摘 RCLI-01：公開後の報告失敗で、出力の存在を伝えない

- 重要度：中。再実行の判断を誤らせる運用上の問題です。保存された牌譜が壊れたという指摘ではありません。
- 対象：`transcode_mjai` の `publish_output` 成功後に行う標準出力への報告。
- 再現：合成した正常な2イベントのmjsonを `mjai wrap` で変換し、標準出力を `/dev/full` に接続します。
- 実測：終了コードは1、完成ファイルは存在し、診断は `No space left on device (os error 28)` のみです。ファイルには有効な注釈付き記録が保存されています。
- 影響：利用者やAIエージェントは変換全体が未完了と判断しやすく、同じ出力先への再実行では非上書きエラーになります。作業書D3の「CLI失敗時に完成物が残らない」という無条件の表現にも一致しません。
- 対応案：保存・検証・公開前の失敗と、公開後の報告失敗を区別します。後者は公開済みであることと出力先を明確に診断し、仕様・DoDの記述と回帰検査を合わせます。すでに公開した正しいファイルを、報告の失敗を理由に黙って削除する対応は避けます。

再現結果は `dist/private-probes/annotated-rust-cli-review/results.json` の `stdout_failure_after_publication` に保存しました。合成入力のみを使用しています。

## 確認した範囲

| 観点 | 実装照合・合成プローブの結果 |
|---|---|
| 原文保持 | `1e-400`、`-0`、Unicodeエスケープを持つイベントの標準→包装→標準がバイト単位で一致 |
| 外側のキー | `event` のUnicodeエスケープ表記は正常に読込み。通常表記とエスケープ表記を併記した重複event/annotationsは拒否 |
| 版・未知項目 | 版の負のゼロ、未知の外側項目、BOM、正常終端後のコメントを拒否 |
| 注釈 | RawValueで取り出した元文字列を別途検査。非有限数値、入れ子の重複、object以外を拒否。原イベントの解析へ注釈を混ぜない |
| 深さと数値字句 | 元イベントと注釈を既存の重複拒否パーサで再検査する経路を確認。型付き整数の小数・指数をValueから文字列へ戻して補正する経路はない |
| 入出力上限 | 入力は共有した有界行読込み。出力は包装を含む行長・件数・LFを含む総量を、書込み前に検査 |
| 正常EOF | end_game後にも入力を読み、末尾の不正やI/O失敗を検査。callback結果は完了まで暫定 |
| 改行 | 末尾改行なしとCRLFを受理。原文内部CRは包装の保存時に明示拒否する修正を確認 |
| 赤牌集計 | 型付きEventの既知牌項目のみを走査し、名前・注釈・任意追加項目は除外 |
| 非上書き | 出力先を事前検査し、最後にhard_linkで新規公開。dangling symlinkの宛先も変更せず失敗し、一時ファイルが残らない |
| 情報公開 | 席別観測の行には `record.raw` 全体や注釈を付けず、既存の `ReplayState::observe` を利用 |

原文往復プローブの入力SHA256は `f729bdeb97e7a3c509d8fe68ce51ce2989b8d0dc4b5783c2eaf83cde83ffd107` です。追加したCLIプローブは9種類の構造・終端条件、原文往復、既存のdangling symlink保護、公開後の報告失敗を対象にしています。

## 既に修正された別の反例

主担当が先に見つけた、標準readerが受理する内部CRをそのまま包むと注釈付きreaderで再読できない問題は、`encode_fragments` が両方の原文に `single_line_fragment` を適用することで修正されました。`wrap_rejects_internal_cr_before_writing_an_unreadable_envelope` がこの境界を対象とします。この発見を本レビューによる新規発見とは数えていません。

## 残る検証範囲

本レビューはコード照合と合成プローブです。固定20事例の全往復、9,240の席別観測、配布物消費、全体CIはそれぞれの検証工程で判定します。全麻雀規則の合法性や得点計算の独立検証、プロセス強制終了・OSクラッシュ後の永続性までは保証しません。低水準のWrite先へ書かれた暫定prefixの取り消しは呼出側の責務です。

## 修正確認

RCLI-01は初回レビュー時点では未解決でした。主担当は公開後の報告失敗について、公開済みの出力先と報告失敗を明記する診断を実装し、仕様・作業書D3へ公開前後の区別を記載しました。Linuxの `report_failure_explicitly_identifies_the_already_published_file` は、旧診断での失敗と修正後の成功を別記録へ保存しています。

独立担当も同じ `/dev/full` 条件を再実行しました。公開後の報告失敗は終了1のままですが、診断は「出力は……に公開済みです。結果報告に失敗しました」と宛先を明示し、保持した出力は別の `mjai analyze --format annotated_mjai` で終了0となりました。あわせて、末尾を壊した入力では終了1・完成ファイルなし・公開済みという診断なしを確認しました。両方とも一時ファイル残存は0件です。

結果は `dist/private-probes/annotated-rust-cli-review/results-fixed.json` に保存し、最初の結果は保持しています。**修正後判定：PASS。** 本レビュー範囲に未解決の重大指摘はありません。公開後の報告失敗でも完成ファイルが存在するという状態は、誤った成功や未公開として扱わず、文書と診断の両方で区別されています。
