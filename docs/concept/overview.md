# コンセプト：すずめ

## 目的

端末でひとりでも遊べる四人リーチ麻雀を、Rustで独自に実装します。
配牌を眺め、手牌を選び、CPUと対局し、役と点数を確認する一連の体験を提供します。
同時に、麻雀の規則をプログラム内の条件分岐に埋め込むだけで終わらせず、
規則の宣言、操作の契約、数学的な性質、実装の検査を追跡できる小さな開発基盤にします。

## 利用者と体験

麻雀の基本を知る利用者が、人間1人・CPU3人で東風戦を進めます。
手牌、河、副露、ドラ表示牌、点数、供託、本場、残りの山を表示します。
その場で可能な操作だけを提示し、不正な入力は理由を表示して受け付け直します。
行入力方式を基本とし、端末制御に依存しない表示も選択できます。

CPUの判断には自分の手牌と公開情報だけを渡します。山の順序や他家の手牌は渡しません。
乱数種を指定した自動対局を用意し、不具合を同じ操作列で再現できるようにします。

## 初版の範囲

四人リーチ麻雀の通常の対局を対象にします。採用する細則は
[ルール仕様](../rules/riichi.md) と `rules/riichi.rules` に宣言します。
赤牌、加槓、途中流局、流し満貫、天和・地和、通信対戦、牌譜形式の互換は初版には含めません。
これはすべての競技団体やオンラインサービスの規則を再現する製品ではなく、
明示した一つのルールで遊び、実装と仕様の関係を検証する試作です。

## 設計の判断基準

1. 対局処理は表示や入力方法を知らず、操作と結果を値で受け渡します。
2. ルールの定数と採否は一箇所に宣言し、生成物の不一致を自動検出します。
3. 不正な操作は状態を変えず、成功した操作は牌と点数の保存条件を満たします。
4. 小さな純粋関数はKaniとLeanで検証し、大きな対局の組合せは通常テストで検査します。
5. 形式検証の成功を、未対象の役判定や対局全体の証明へ拡大して説明しません。

## 参考にした公開資料

- [mahjong-tui](https://github.com/k-jun/mahjong-tui)：端末上の四人麻雀という体験と牌の省略表記。
- [simplified-mahjong-yixuan](https://github.com/EconomicScienceInstitute/computational-economics-simplified-mahjong-yixuan)：簡略化した麻雀と意思決定実験の切り分け。
- [mahjong-ai](https://github.com/clarkwkw/mahjong-ai)：ゲーム・プレイヤー・判断方式・得点処理の責務分離。
- [MiHaJong](https://github.com/MihailJP/MiHaJong)：採用するローカル規則を明示する必要性。
- [Go-Lean](https://github.com/Mal-Pat/Go-Lean)：操作を受ける純粋な状態遷移と、表示・通信の分離。
- [Kani](https://github.com/model-checking/kani)：実際のRust関数を任意入力で検査する方法。

上記の説明から設計上の観点を得ています。これらのゲームコードや画像を取り込んではいません。
